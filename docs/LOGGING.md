# 로그 레벨 (Logging Levels)

> 또맛또(TMT) 백엔드의 로그 레벨 기준. (TMT-354)
> 이 문서의 확정 = 본 PR에 BE 팀원 approve. 변경은 PR로만.

## 1. 왜 정의하는가

**로그 레벨이 Sentry 이벤트 경계를 그대로 결정한다.** `logback-spring.xml`의
`minimumEventLevel=ERROR`라 ERROR로 남긴 것만 이벤트가 되고, 그 이벤트가 온콜 봇(TMT-311)의
분석 대상이 된다. 레벨을 잘못 정하면 두 방향으로 틀린다.

- **과하면** — 조치할 수 없는 건이 쌓여 알림이 무뎌지고, 봇이 매번 분석에 들어가 비용만 나간다
- **모자라면** — 사용자가 서비스를 못 쓰는 상태를 아무도 모른다

## 2. 원칙 — "누가 언제 봐야 하는가"

레벨은 **누가 고치느냐**가 아니라 **사용자에게 무슨 일이 일어났고 누가 언제 봐야 하는가**로 정한다.

| 레벨 | 뜻 | Sentry |
|---|---|---|
| `ERROR` | 지금 사람이 조치해야 한다 | 이벤트 |
| `WARN` | 지금은 아니지만 추세를 봐야 한다 — 쌓이면 신호 | breadcrumb |
| `INFO` | 정상 흐름의 기록 | breadcrumb |
| `DEBUG` | 개발 중에만 본다 (local 프로필) | X |

ERROR의 판정 기준은 둘이다. **둘 중 하나만 맞아도 ERROR다.**

1. **사용자 요청이 5xx로 끝났다** — 남의 장애가 원인이어도 마찬가지다.
   우리가 해결할 수 없다는 것이 몰라도 된다는 뜻은 아니다. 오히려 해결할 수 없으면 더 알려야 한다
2. **5xx가 아니어도 기능이 지속적으로 불가하다** — 요청은 200으로 끝나도(배치·폴백) 기능은 결손이다

## 3. 상황별 기준

### 3-1. 응답으로 나간 실패

| 상황 | `ErrorType` | 상태 | 레벨 |
|---|---|---|---|
| 서버 결함 | `INTERNAL` | 500 | `ERROR` |
| 설정·키 누락 (§3-3) | `INTERNAL` | 500 | `ERROR` |
| 외부 의존 응답 없음 | `EXTERNAL_UNAVAILABLE` | 502 | `ERROR` |
| 기능 일시 불가 | `SERVICE_UNAVAILABLE` | 503 | `ERROR` |
| 요청 형식이 틀렸다 | `VALIDATION` | 400 | `WARN` |
| 호출 상한 초과 | `RATE_LIMITED` | 429 | `WARN` (아직 쓰는 자리 없음) |
| 인증·권한 없음 | `UNAUTHORIZED` · `FORBIDDEN` | 401 · 403 | `INFO` |
| 없는 리소스 | `NOT_FOUND` · `GONE` | 404 · 410 | `INFO` |
| 비즈니스 충돌 | `CONFLICT` · `UNPROCESSABLE` | 409 · 422 | `INFO` |

**4xx가 둘로 갈리는 이유.** 401·404·409는 사용자에게 **예상된 실패**다. 하루에 수천 건 나도
정상이고, 서버가 제 일을 한 결과다 — 정상 흐름이니 `INFO`.

반면 400(검증·파싱·타입 불일치)과 429는 **정상 클라이언트라면 나오지 않는다.** 급증하면
FE와 계약이 어긋났거나 누가 잘못된 방식으로 부르고 있다는 신호라, 추세를 봐야 하므로 `WARN`.
`?limit=abc` 하나에 500이 나가던 자리가 여기다 (TMT-343).

**429는 방향을 헷갈리지 않는다.** `RATE_LIMITED`는 **우리가 사용자에게** "너무 자주 부른다"고
말하는 코드다. 외부 API가 **우리에게** 429를 주는 것은 사용자 잘못이 아니라 우리 쿼터가 소진된
것이므로, 그대로 429로 내보내면 사용자는 자기가 많이 눌렀다고 읽는다. 그때는 503이 정직하다
(§3-2 폴백 소진). 지금은 사용자별 호출 제한이 없어 `RATE_LIMITED`를 쓰는 자리가 없다.

`INFO`로 내려도 정보가 사라지지 않는다. `minimumBreadcrumbLevel=INFO`라 breadcrumb으로
이벤트에 딸려 가고, **오히려 "사용자가 무슨 요청을 하다 죽었나"가 남아 분석 입력이 좋아진다.**

### 3-2. 응답으로 나가지 않는 실패

| 상황 | 레벨 | 근거 |
|---|---|---|
| 클라이언트가 응답 수신 중 연결을 끊음 | `WARN` | 서버가 고칠 것이 없다. 화면 이탈·새로고침으로 흔히 난다 |
| 폴백으로 복구된 실패 (다음 프로바이더 성공) | `WARN` | 사용자 영향 없음. 주 프로바이더가 흔들린다는 추세 신호 |
| 단건 작업 실패 (배치의 한 매장 등) | `WARN` | 그 데이터의 문제일 수 있다. 다음 주기가 다시 줍는다 |
| **폴백을 전부 소진** | `ERROR` | 요청이 200으로 끝나도 기능은 결손이다 (원칙 2) |
| **작업 전체가 같은 원인으로 실패** | `ERROR` | 단건 실패와 다르다. 기능이 통째로 멈춰 있다 |

### 3-3. 설정·키 누락

**기동 시점에 이미 아는 사실은 기동 시점에 알린다.** 요청이 올 때까지 기다렸다가 사용자가
겪게 하지 않는다.

| 상황 | 시점 | 레벨 |
|---|---|---|
| 폴백 프로바이더 중 일부만 활성 | 기동 | `WARN` — 기능은 되지만 여력이 없다 |
| 기능에 필요한 키가 전부 없음 | 기동 | `ERROR` — 그 기능은 통째로 불가하다 |
| 키 없는 상태에서 실제 호출이 들어옴 | 런타임 | `ERROR` (§3-1 설정 결함) |

기동 실패(fail fast)로 막는 값은 이 표의 대상이 아니다. `JWT_SECRET`·`ADDRESS_TOKEN_SECRET`·
DB 접속 정보처럼 **prod에서 기본값을 두지 않은 값**은 앱이 뜨지 않으므로 이벤트가 될 수 없고,
다운 트리거(health 폴링)가 잡는다.

카카오·juso·LLM 키는 **기본값을 비워 두어 기동은 되게 한다.** 로그인이 막혀도 서비스를
둘러볼 수는 있어야 하고, 주소 검색·AI 요약은 부분 기능이라 그것 때문에 서버 전체가 뜨지 못하는
편이 더 나쁘다.

## 4. 규칙

### 4-1. 이벤트는 한 곳에서 발행한다

같은 사건을 어댑터와 `ExceptionAdvice`가 각각 ERROR로 남기면 **한 장애가 두 이슈가 된다.**
역할을 나눈다.

- **어댑터·서비스** — `WARN`으로 맥락을 남긴다 (공급자 오류 코드, 실패한 프로바이더 이름 등).
  breadcrumb으로 이벤트에 딸려 가므로 정보는 사라지지 않는다
- **`ExceptionAdvice`** — `ErrorType`을 보고 레벨을 정해 이벤트를 발행한다

예외는 §3-3의 기동 로그와 §3-2의 응답 밖 실패뿐이다. 둘 다 요청 경로 밖이라 어드바이스가 볼 수 없다.

### 4-2. 예외가 있으면 throwable을 넘긴다

```kotlin
logger.error(e) { "카카오 토큰 교환 거절 - status=${e.status}" }   // O
logger.error { "카카오 토큰 교환 거절 - status=${e.status}" }      // X
```

스택 없이 메시지만 올라간 이벤트는 **봇도 사람도 호출 지점을 짚지 못한다.** 그루핑도
메시지 문자열에 의존해 같은 원인이 여러 이슈로 흩어진다.

### 4-3. 설정 결함과 외부 장애를 같은 코드로 내지 않는다

우리가 키를 넣지 않은 것과 카카오가 죽은 것은 원인이 정반대인데 지금은 같은
`AUTH_KAKAO_UNAVAILABLE`(502)로 나간다. 카카오는 멀쩡한데 "카카오가 응답하지 않습니다"라고
사용자에게 말하는 셈이다. 502는 "잠시 뒤 다시"라는 뜻이라 FE가 재시도해도 되는 줄 안다.

`ErrorCode` 이름은 응답의 `code` 값이자 클라이언트 분기 기준이라 **이름을 바꾸지 않고 새 코드를
추가한다** (CLAUDE.md §API 계약).

| 원인 | 코드 | 상태 |
|---|---|---|
| 카카오가 죽음·응답 이상 | `AUTH_KAKAO_UNAVAILABLE` | 502 |
| 카카오 키 누락 | `AUTH_KAKAO_MISCONFIGURED` | 500 |
| juso 장애 | `ADDRESS_PROVIDER_UNAVAILABLE` | 502 |
| juso 승인키 누락 | `ADDRESS_PROVIDER_MISCONFIGURED` | 500 |

### 4-4. `ErrorType`은 로그 레벨의 근거가 아니다

`ErrorType`은 **응답 상태 코드**를 가르는 근거다. "외부 의존이 원인이니 우리 알림은 울리지
않는다"로 확장해 쓰지 않는다 — 502와 500은 클라이언트에게 다른 상태지만, **사용자에게는 둘 다
'안 됨'이다.**

### 4-5. 로그에 값을 싣지 않는다

사용자가 보낸 값·토큰·키는 메시지에 넣지 않는다. 무엇이 틀렸는지는 파라미터 이름으로 충분하고,
값은 그대로 응답·로그·Sentry 이벤트에 실려 나간다. (기존 `ExceptionAdvice` 주석의 판단을 규칙으로 옮긴 것)

## 5. 이 문서로 정해지지 않는 것

- **`maxBreadcrumbs`(현재 100)** — 요청 경로에 INFO를 넣은 뒤 실제 이벤트 크기를 보고 조정한다.
  이벤트가 커지면 봇의 분석 입력 토큰이 늘어 비용이 된다
- **서킷이 열린 동안의 이벤트 양** — 서킷 열림은 `ADDRESS_PROVIDER_UNAVAILABLE`(502)로 응답에
  나가므로 §3-1대로 `ERROR` 이벤트가 된다. juso IP 차단처럼 차단이 길게 유지되면 그동안 주소를
  검색하는 사용자마다 이벤트가 하나씩 쌓인다. 배포 후 실제 분포를 보고, 억제가 필요하면 서킷
  열림에 별도 `ErrorCode`를 주는 안을 검토한다 (별도 티켓)
- **`SENTRY_DSN` 누락 감지** — DSN이 비면 SDK가 no-op이라 **수집이 꺼진 것을 수집기로 알 수 없다.**
  기동 로그나 봇의 "일정 시간 이벤트 0건" 감시 같은 다른 장치가 필요하다 (별도 티켓)
